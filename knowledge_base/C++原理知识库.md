## 语言核心（CORE）

### [CPP-CORE-01] RAII 与资源管理

- **是什么**：资源获取即初始化——用对象生命周期管理资源，构造时获取、析构时释放。
- **核心要点**：① 栈对象析构保证执行（含异常路径）；② `std::lock_guard`/`std::unique_lock` 是 RAII 管锁；③ 智能指针是 RAII 管堆内存；④ 文件句柄、socket fd 都应封装成 RAII 类；⑤ 析构函数不抛异常。
- **项目映射**：`bridge_node.py` 的 `_tcp_send` 手动管 socket（出错关闭重建）——C++ 重写版应封装 `TcpClient` 类，析构自动 `close(fd)`，异常路径不泄漏。
- **典型问题**：RAII 是什么？为什么 C++ 不用 GC 也能不泄漏？
- **解答要点**：资源的释放绑定到作用域结束，编译器生成析构调用，无需运行时追踪。对比：Python 靠引用计数+GC，C++ 靠作用域确定性释放——这对控制循环很重要（析构时机可预测）。
- **更新日期**：2026-09-01（初版）

### [CPP-CORE-02] 值语义、引用与 const 正确性

- **是什么**：C++ 默认值传递（拷贝），引用是别名；`const` 是契约。
- **核心要点**：① 按值传参会拷贝，大对象用 `const &`；② `std::string`/`std::vector` 参数惯例：入参 `const &`，要转移所有权时按值+`std::move`；③ `const` 成员函数承诺不修改对象状态；④ 返回局部变量的引用是悬垂引用（UB）。
- **项目映射**：桥接的 `_nav_target = (0.0, 0.0)` 元组拷贝就是值语义；C++ 版速度目标用 `struct VelCmd {double v, w;}` 值传递即可（16 字节，拷贝比间接寻址更快）。
- **典型问题**：什么时候按值传参？`const &` 和值传递怎么选？
- **解答要点**：小对象（≤2 个寄存器宽）直接值传递最快；大对象 `const &`；要"吃掉"参数时按值传 + 移动进成员。
- **更新日期**：2026-09-01（初版）

### [CPP-CORE-03] 移动语义与右值引用

- **是什么**：`T&&` 绑定将亡对象，`std::move` 把资源所有权"偷"过来，避免深拷贝。
- **核心要点**：① `std::move` 本身不移动，只是转换为右值引用；② 移动后的对象处于"有效但未指定"状态；③ 移动构造应 `noexcept`（否则 `vector` 扩容退回拷贝）；④ 返回局部变量靠 RVO/NRVO，别手动 `std::move(return)`。
- **项目映射**：点云消息（百万级 float）在 C++ 节点间传递时，移动语义/指针共享避免拷贝是性能关键（对应 CPP-ROS-04 零拷贝）。
- **典型问题**：`std::move` 做了什么？移动后对象还能用吗？
- **解答要点**：它是 `static_cast<T&&>`；移动后对象可析构、可重新赋值，但读其内容是未定义的语义（标准保证有效不保证值）。
- **更新日期**：2026-09-01（初版）

### [CPP-CORE-04] 智能指针选型

- **是什么**：`unique_ptr`（独占）/`shared_ptr`（引用计数共享）/`weak_ptr`（打破循环）。
- **核心要点**：① 默认 `unique_ptr`，零开销；② `shared_ptr` 有原子计数开销，别滥用；③ 循环引用用 `weak_ptr`；④ 不要在两个地方用裸指针 `new` 同一个对象再交给两个 `shared_ptr`；⑤ 工厂函数返回 `unique_ptr`。
- **项目映射**：Nav2 的插件体系（controller/critic 都是 plugin 动态加载）底层就是多态 + 智能指针管理生命周期。
- **典型问题**：`shared_ptr` 线程安全吗？
- **解答要点**：控制块（计数）的增减是原子的，但**指向的对象**不是线程安全的；两个线程同时读写同一对象仍需加锁。
- **更新日期**：2026-09-01（初版）

### [CPP-CORE-05] 虚函数与多态的代价

- **是什么**：虚函数通过 vtable 间接调用实现运行时多态。
- **核心要点**：① 每个含虚函数的类有 vtable，对象含 vptr（8 字节）；② 虚调用无法内联、可能破坏指令缓存；③ 析构函数必须虚（基类指针 delete 派生对象否则 UB）；④ 高频小函数（如每关节每拍的变换）避免虚化，用模板（CRTP）或直接具体类型。
- **项目映射**：DWB 的 critics 是插件多态（低频，10Hz，虚调用开销无所谓）；但 1kHz 运控循环里的计算绝不加虚函数——这就是"频率决定设计"。
- **典型问题**：虚函数的开销在哪？热路径要不要避免？
- **解答要点**：开销在间接跳转 + 阻止内联 + 缓存不友好；10Hz 路径无所谓，1kHz+ 热路径应避免或用编译期多态。
- **更新日期**：2026-09-01（初版）

### [CPP-CORE-06] 未定义行为（UB）清单

- **是什么**：标准不保证任何结果的代码，编译器可以做任何事（包括"看起来正常"）。
- **核心要点**：常见高频 UB——① 解引用空/悬垂指针；② 有符号整数溢出；③ 数组越界（`std::vector::operator[]` 不检查）；④ 数据竞争（两线程读写同一内存且无同步）；⑤ 使用未初始化变量；⑥ 基类指针 delete 派生对象但析构非虚。
- **项目映射**：字节序错误发送（INTV-COM-01）的对端视角就是"按错误布局解释内存"——协议两端结构体布局/字节序不一致与 UB 同源：都是"内存解释契约被违反"。
- **典型问题**：写一段有 UB 的代码并说明后果？数据竞争为什么是 UB？
- **解答要点**：数据竞争下编译器可以假设无竞争做优化（把变量缓存在寄存器），导致现象诡异难复现；用 TSan（ThreadSanitizer）检测。
- **更新日期**：2026-09-01（初版）

## 并发（CON）

### [CPP-CON-01] 线程与互斥锁（mutex/lock_guard）

- **是什么**：`std::thread` 启动线程，`std::mutex` + `lock_guard` 保护共享数据。
- **核心要点**：① `lock_guard` 构造加锁析构解锁（RAII），异常安全；② 锁的粒度尽量小——只锁共享状态读写，别把 IO 包进临界区；③ 多锁按固定顺序加锁防死锁；④ 锁保护的是"数据"不是"代码"——所有访问该数据的路径都要持锁。
- **项目映射**：`bridge_node.py` 的 `_nav_lock` 保护 `_nav_target`（回调写、发送线程读）；C++ 版同构：`std::mutex + lock_guard`，临界区只做 16 字节赋值。
- **典型问题**：`lock_guard` 和 `unique_lock` 区别？临界区应该多小？
- **解答要点**：`unique_lock` 可中途 `unlock()/lock()`、可配条件变量，略慢；临界区只包含共享内存的读写，发送/日志等副作用放锁外。
- **更新日期**：2026-09-01（初版）

### [CPP-CON-02] 生产者-消费者与条件变量

- **是什么**：`condition_variable` 让线程在条件不满足时挂起等待，避免忙等。
- **核心要点**：① `wait` 必须带谓词（防虚假唤醒）；② 等待/通知都要持同一把锁；③ 单生产者单消费者 + 定长缓冲可用无锁环形队列；④ `notify_one`/`notify_all` 后不需要持锁。
- **项目映射**：桥接的"回调存目标值 → 独立线程 50Hz 消费"本质是生产者-消费者解耦（只是用定频节拍代替了条件变量唤醒）；C++ 重写可保持定频（控制回路要的是节拍确定性，不是尽快响应）。
- **典型问题**：为什么 `wait` 要放 while/谓词里？什么是虚假唤醒？
- **解答要点**：操作系统允许 `wait` 无理由返回（实现层面），且多消费者场景被唤醒时条件可能已被别人消费；谓词重查是唯一正确写法。
- **更新日期**：2026-09-01（初版）

### [CPP-CON-03] 原子操作与内存序

- **是什么**：`std::atomic` 保证读写不被撕裂，内存序控制其他内存操作的可见顺序。
- **核心要点**：① `atomic` 免锁但有硬件成本（总线锁定/缓存一致性流量）；② 默认 `memory_order_seq_cst` 最安全最慢；③ 常见优化：单生产者单消费者标志用 `release/acquire`；④ 非原子的"读-改-写"（如 `i++`）即使 `int` 也竞争。
- **项目映射**：桥接的 `rclpy.ok()` 循环退出标志、看门狗时间戳这类单写多读状态，C++ 版可用 `std::atomic<double>`（读侧无锁采样）。
- **典型问题**：`volatile` 能代替 `atomic` 吗？
- **解答要点**：不能。`volatile` 只禁止编译器优化掉读写（用于 MMIO），不提供原子性和线程间顺序；多线程同步必须用 `atomic` 或锁。
- **更新日期**：2026-09-01（初版）

### [CPP-CON-04] GIL 对比：为什么 C++ 能治好桥接的饿死

- **是什么**：CPython 的 GIL 让同一进程内同一时刻只有一个线程执行 Python 字节码。
- **核心要点**：① GIL 按时间片轮转，但持有 GIL 的线程在调用不释放它的 C 扩展时会长时间霸占；② IO 等待会释放 GIL，纯计算/序列化不会；③ C++ 多线程是真并行（多核同时执行）；④ Python 高频回调场景，关键路径要么进程隔离要么换 C++。
- **项目映射**：抽搐事故时序根因（INTV-COM-02）：LCM 高频回调霸 GIL，cmd_vel 发送被饿死到 ~10Hz。Python 侧已用"回调只存值+独立线程"缓解；C++ 重写版从根本上消除 GIL 因素，50Hz 节拍硬保证。
- **典型问题**：Python 多线程为什么跑不满多核？你的项目里怎么绕过的？
- **解答要点**：GIL 互斥字节码执行；绕过方式：① 线程职责分离（短临界区存值）② 计算下沉到释放 GIL 的 C 库（numpy/open3d）③ 关键路径进程化或 C++ 化。
- **更新日期**：2026-09-01（初版）

### [CPP-CON-05] 实时性与线程优先级

- **是什么**：实时性 = 截止期可保证，不是"快"；Linux 用 `SCHED_FIFO/RR` + 优先级。
- **核心要点**：① `chrt -f` 设 FIFO 实时调度；② 实时线程里禁止动态内存分配/锁争用/缺页（`mlockall`）；③ 非实时线程优先级再高也受 CFS 带宽影响；④ `nice`/`cpuset` 绑核隔离。
- **项目映射**：ICP 的 7 个 open3d 线程抢核拖累 `controller_server` 10Hz 节拍（INTV-INC-02）——治法就是绑核/限线程隔离实时性敏感的控制节点。
- **典型问题**：怎么保证控制循环节拍不被干扰？
- **解答要点**：三层：绑核隔离（cpuset）、限制干扰源的线程数（OMP_NUM_THREADS）、关键线程提优先级（chrt）+ 避免临界路径分配内存。
- **更新日期**：2026-09-01（初版）

## 网络（NET）

### [CPP-NET-01] TCP 流语义与粘包（定长帧）

- **是什么**：TCP 是字节流，没有消息边界；`send` 两次 24 字节，对端可能一次 `recv` 收 48 字节。
- **核心要点**：① 应用层必须自己定帧：定长帧（最简单）/长度头帧/分隔符帧；② `recv` 返回值可能小于请求长度，必须循环读满；③ UDP 保留消息边界但不可靠；④ 半关闭与 `EOF`（recv 返回 0）。
- **项目映射**：桥接→UpBoard 用**定长 24 字节帧**（3×double）：无帧头帧尾、按 24 切片即可；前提是指令频率恒定（50Hz）且内容无歧义。
- **典型问题**：TCP 粘包怎么解决？你为什么选定长帧？
- **解答要点**：三种方案各有权衡；定长帧零解析开销、适合固定结构控制指令；长度头帧适合变长数据。
- **更新日期**：2026-09-01（初版）

### [CPP-NET-02] Nagle 算法与 TCP_NODELAY

- **是什么**：Nagle 把小包攒着等 ACK 或凑满 MSS 再发，减少网络上的小包数量。
- **核心要点**：① 延迟可达 40ms（ delayed ACK 交互下可到 200ms）；② 控制回路/交互式应用必须 `setsockopt(TCP_NODELAY)`；③ 大吞吐批量传输反而该保留 Nagle；④ `send` 返回不代表对端收到，只代表进了内核缓冲。
- **项目映射**：`_tcp_send` 建连时即设 `TCP_NODELAY=1`——50Hz 指令每包 24 字节，正是 Nagle 最喜欢攒的小包，不开则指令突发成"一阵一阵"。
- **典型问题**：你的控制指令延迟怎么保证的？
- **解答要点**：TCP_NODELAY 关攒包 + 定频发送（不依赖事件触发）+ 接收端看门狗检测断流；延迟 = 序列化(~μs)+网络(<1ms)+对端解析。
- **更新日期**：2026-09-01（初版）

### [CPP-NET-03] 字节序、对齐与序列化

- **是什么**：多字节整数在不同 CPU 上高低字节顺序不同（x86 小端/网络序大端）；结构体有内存对齐填充。
- **核心要点**：① 跨机通信必须显式约定字节序并转换（`htonl/htole` 或 pack 格式符）；② 结构体不要直接二进制发送——对齐填充因编译器/平台而异，用 `#pragma pack(1)` 或显式序列化；③ 浮点也有字节序问题（IEEE 754 位模式按字节反转）；④ Python `struct` 的 `<`/`>` 前缀就是干这个的。
- **项目映射**：P0 事故（INTV-COM-01）：`'>3d'`（大端）发给 x86 直读内存的 UpBoard，指令变随机数→狗乱动；改 `'<3d'` 解决。铁律：**序列化格式由对端的解释方式决定**。
- **典型问题**：怎么判断本机字节序？直接发结构体有什么风险？
- **解答要点**：联合体/`union{int; char[4]}` 看首字节；风险 = 对齐填充 + 字节序 + 编译器布局三重不确定，正确做法是逐字段显式序列化。
- **更新日期**：2026-09-01（初版）

## 性能（PERF）

### [CPP-PERF-01] 缓存局部性与数据布局

- **是什么**：CPU 访问内存经缓存层级（L1~L3），连续访问命中率高，随机访问惩罚数十倍。
- **核心要点**：① 数组连续遍历 >> 链表跳指针；② 结构体数组（AoS）vs 数组结构体（SoA）：批处理同字段用 SoA；③ 伪共享：两线程写同一缓存行的不同变量也互相拖累（对齐到 64B）；④ 点云处理优先降采样/分块而不是硬算。
- **项目映射**：ICP 对百万级点云每拍做体素降采样（0.1m）再配准——先降维再计算是点云管线的第一性能原则；`global_localization` 74% CPU 的大头就在这。
- **典型问题**：遍历 `vector<Particle{x,y,z,...}>` 只用 x，为什么慢？怎么优化？
- **解答要点**：每个元素加载整条缓存行只用一小段；SoA（`vector<float> xs`）或分块处理，让缓存行利用率接近 100%。
- **更新日期**：2026-09-01（初版）

### [CPP-PERF-02] 性能分析方法与工具

- **是什么**：先测量再优化；自顶向下定位热点。
- **核心要点**：① `loadavg`/`top` 看宏观是否过载；② `ps --sort=-%cpu` 找大户进程；③ `perf top`/`perf record` 找函数级热点（C++）；④ py-spy 采样 Python 火焰图；⑤ 判断"贵是否有道理"：原生计算（算法降维）vs 框架开销（重写/降频）；⑥ 优化后必须回归验证行为不变。
- **项目映射**：CPU 过载诊断全流程（INTV-INC-02）：loadavg 12.7 → ps 排序 → 线程级 `ps -T` 发现 open3d 7 线程 → 结论"删掉无人用的相机（41%）+ 限 ICP 线程"，而不是重写。
- **典型问题**：程序慢你怎么查？
- **解答要点**：四步：确认瓶颈层级（CPU/IO/锁）→ 找热点进程 → 找热点函数 → 区分"必要计算"与"可删开销"，优先删和降频，最后才谈重写。
- **更新日期**：2026-09-01（初版）

## ROS 2 C++（ROS）

### [CPP-ROS-01] rclcpp 执行模型（executor/回调）

- **是什么**：rclcpp 节点把订阅/定时器注册为回调，由 executor 单线程（默认）或多线程调度执行。
- **核心要点**：① 默认 `SingleThreadedExecutor`：所有回调串行，一个慢回调阻塞全部——与 Python GIL 饿死同构；② `MultiThreadedExecutor` + `ReentrantCallbackGroup` 可并行，但要自己处理线程安全；③ 回调里不做长耗时计算，重活丢给工作线程（和桥接的重构思路一致）；④ `spin` 的退出靠 `rclcpp::ok()` + 信号。
- **项目映射**：桥接 Python 版"回调只存值、发送独立线程"的设计，C++ 版原样移植：订阅回调只写共享目标值（锁/原子），定时回调 50Hz 定频发送。
- **典型问题**：ROS 2 节点收到消息的处理是并发的吗？怎么让耗时任务不阻塞回调？
- **解答要点**：默认串行；耗时任务用独立线程 + 线程安全队列交接，或换多线程执行器并显式管理回调组。
- **更新日期**：2026-09-01（初版）

### [CPP-ROS-02] QoS 与 /tf_static 的 transient_local

- **是什么**：QoS 定义通信质量策略：历史深度、可靠性（reliable/best_effort）、持久性（volatile/transient_local）等。
- **核心要点**：① 传感器数据用 `sensor_data` 预设（best_effort + keep_last 5）：允许丢帧换低延迟；② `transient_local` = DDS 持久化，晚加入的订阅者能收到历史消息——`/tf_static` 靠它让后启动的节点也能拿到静态变换；③ 收发两端 QoS 不兼容则连不上（静默无消息，常见坑）；④ 控制指令应 reliable。
- **项目映射**：相机禁用时确认 `camera_link` TF 不受影响——静态外参走 `/tf_static`（transient_local），由 `robot_state_publisher` 发布，任何时刻加入的节点都能拿到。
- **典型问题**：为什么激光话题经常收不到消息？`/tf_static` 为什么后启动的节点也能收到？
- **解答要点**：先查 QoS 兼容性（传感器多为 best_effort，订阅端用 reliable 就连不上）；`/tf_static` 是 transient_local，DDS 保存样本供晚订阅者回放。
- **更新日期**：2026-09-01（初版）

### [CPP-ROS-03] tf2 缓冲与 TF 树原则

- **是什么**：tf2 维护带时间戳的变换树，支持任意两帧间插值查询；原则：每条边只有一个发布源。
- **核心要点**：① TF 树不允许环、不允许同一边多源（多源按时间戳混用导致抖动）；② 查询要带时间戳容差（`transform_tolerance`），过旧数据报 extrapolation 错；③ 变换链越短查询越稳；④ 静态变换发 `/tf_static` 一次，动态变换持续发。
- **项目映射**：孤儿进程事故（INTV-INC-01）：两个 `transform_fusion` 同发 `map→odom`，双源混用导致位姿抖动——TF 单源原则被破坏的活教材。
- **典型问题**：TF 报 extrapolation 错误怎么排查？两个节点发同一条 TF 会怎样？
- **解答要点**：先查发布频率/时间戳是否落后（`tf2_monitor`/`view_frames`）；双源时监听端按时间戳取最新的，两源交替占优就抖动，必须保证单源。
- **更新日期**：2026-09-01（初版）

### [CPP-ROS-04] 零拷贝与进程内通信

- **是什么**：大消息（点云/图像）避免序列化-拷贝开销：同进程用 `unique_ptr` 发布所有权转移；跨进程用 DDS 共享内存（iceoryx）。
- **核心要点**：① `publisher->publish(std::move(msg))` 转移所有权，避免拷贝；② 订阅回调拿 `const &` 或按值（配合移动）；③ 组件（component）合成一个进程可启用进程内通信；④ 点云管线能少拷贝一次是一次（百万点 × 16 字节 = 16MB/帧）。
- **项目映射**：`/cloud_registered_body` 点云进代价地图的链路，若未来 C++ 化，`unique_ptr` 发布 + 订阅端只读引用是基本要求；当前 Python 侧 open3d 转 numpy 已有隐式拷贝成本。
- **典型问题**：点云话题带宽很高，怎么降低通信开销？
- **解答要点**：优先算法侧降采样（源头减量），其次零拷贝发布/共享内存传输，最后才考虑压缩编码（压缩本身也耗 CPU）。
- **更新日期**：2026-09-01（初版）

## 构建（BUILD）

### [CPP-BUILD-01] CMake/colcon 与 symlink-install

- **是什么**：colcon 是 ROS 2 的多包构建编排，底层调 CMake（C++）/setuptools（Python）。
- **核心要点**：① `--symlink-install`：Python/launch/yaml 等资源在 install 目录建软链，改源码免重建；C++ 编译产物不受此待遇；② 新增资源文件/改 `package.xml`/`setup.py` 必须重新 build；③ `colcon build --packages-select <pkg>` 单包加速迭代；④ `install/setup.bash` 是环境叠加（overlay）。
- **项目映射**：本工作区为 symlink-install——改 `navigation_launch.py`、`bridge_node.py`、`nav2_3d_params.yaml` 重启即生效（运维实测惯例）；验证方法 `ls -la install/...` 看是否软链。
- **典型问题**：改了配置不生效怎么排查？
- **解答要点**：三查：是否软链模式、运行时 source 的是不是这个工作区的 setup、有没有旧进程没退（孤儿进程吃的是旧代码）。
- **更新日期**：2026-09-01（初版）

### [CPP-BUILD-02] ABI 兼容与 SO 版本

- **是什么**：ABI 是二进制层面的接口契约（函数符号、类布局、vtable 顺序）；改头文件不一定破坏源码兼容之外的二进制兼容。
- **核心要点**：① 加虚函数/改成员顺序 = 破坏 ABI，所有依赖方必须重编；② `dlopen` 插件（Nav2 plugin 机制）对 ABI 敏感，插件与宿主必须同编译器同标志构建；③ `extern "C"` 冻结符号修饰；④ ROS 发行版之间（Foxy/Humble）rclcpp ABI 不兼容，不能混装。
- **项目映射**：Nav2 的 controller/critic 插件加载依赖 pluginlib——自研插件（未来若写自定义 critic）必须与系统 Nav2 同版本构建，否则加载即崩或行为异常。
- **典型问题**：改了基类加一个虚函数，只重编基类所在库行吗？
- **解答要点**：不行。vtable 布局变化波及所有派生类和持有该类型对象的代码，必须全量重编——这就是 ABI 破坏。
- **更新日期**：2026-09-01（初版）
